研究路线和阶段状态见[主计划](../Plan/面向成像卫星任务调度的多智能体协作自动算法设计.md)。P1验收和后续任务见[P1阶段计划](../Plan/mechanisms/P1-可运行求解器起点.md)、[P2阶段计划](../Plan/mechanisms/P2-五角色协作演化.md)。

## 一、共享方法合同

### 1.1 两阶段接口与职责

实例初始化和重分配均由A/B/C完成。每个模块版本包含两阶段策略，随本模块一起演化。

```text
A.initial_assign(problem, api, budget, rng) -> Assignment
A.search_reassignment(problem, api, state, feedback, evaluator, budget, rng) -> MoveTrial | None

B.search_initial(problem, api, view, evaluator, budget, rng) -> InitialTrial
B.search_initial_local(problem, api, view, context, feedback, evaluator, budget, rng) -> LocalTrial | None
B.search_reassignment(problem, api, view, context, feedback, evaluator, budget, rng) -> LocalTrial | None
B.search_calibration(problem, api, view, context, feedback, evaluator, budget, rng) -> LocalTrial | None

MoveEvaluator.evaluate(base, move) -> MoveTrial
MoveEvaluator.calibrate(base) -> MoveTrial
MoveEvaluator.checkpoint(trial)
InitialEvaluator.evaluate(priorities) -> InitialTrial
LocalEvaluator.evaluate(plan) -> LocalTrial
LocalEvaluator.rebuild(priorities, preferred_window_tasks) -> LocalTrial

C.build(problem, api, view, priorities, budget, rng) -> SatSchedule
C.apply_local(problem, api, view, context, plan, budget, rng) -> LocalResult
C.rebuild(problem, api, view, context, priorities, budget, rng) -> SatSchedule
```

- **A** 根据窗口、负载等问题数据给出全部任务的初始归属，允许`None`。初始化阶段禁止通过C试探跨星迁移。重分配读取当前完整调度，提出转移、交换、放弃或分配无归属任务的差分。A的编辑权限限于任务归属。
- **B** 决定本星任务的取舍、顺序和局部搜索，可经运行时反复试评C。重分配可选择全部本星归属任务，任务归属保持不变。
- **C** 按B给出的顺序构造本星时间轴，局部编辑限于B授权的任务。

A和B分别实现两个阶段的策略，A1/A2的重分配和B1/B2的局部策略也各自实现。候选访问、试评门禁和问题验证共用。手工B用独立入口做初始化局部改进。B3初始化采用来源单星混合搜索，不另跑初始化局部改进。B3在重分配中用快速修补或回退搜索做常规调整，在全星校准时单独运行来源种群搜索。

- `state`和本星`view`为只读快照。`Assignment`中每个任务至多有一个owner，非空owner须有合法观测候选。
- `Move`包含`base_state_hash`、归属差分`edits`、额外修复卫星和全星校准标记。只重排时可仅指定修复卫星。全星校准覆盖全部卫星并保留归属。单次归属变更涉及的任务数不限，2026-11-04已取消暂定的4个额外任务上限。
- `LocalPlan`包含`base_view_hash`、允许移除或改时刻的`release`集合及有序的`reconsider`列表。C只能在授权范围内编辑。已调度任务重插须同时列在两者中，C暂不调度的任务保留原owner。

各任务规模使用相同的两阶段调用顺序。各阶段仅使用本阶段策略。

```text
initialize_schedule:
  A.initial_assign
  各星 B.search_initial -> 反复试评 C.build -> 选择一个候选
  各星 B.search_initial_local -> 试评 C.apply_local 或 C.build，context.phase = Phase.INIT

重分配循环:
  A.search_reassignment -> 可反复试评完整移动及其后续候选
  受影响星 B.search_reassignment -> 试评 C.apply_local 或 C.rebuild，context.phase = Phase.REASSIGN
  来源策略需要时：全星 B.search_calibration -> 试评 C.rebuild
```

运行时调用C试评，检查任务、卫星、编辑权限、可行性和截止时间。试评不提交时间轴。A/B只能返回或保存本次调用试评所得候选，返回后入口失效。A可比较或链式试评，也可用`MoveEvaluator.checkpoint`保存已选可行候选供截止时返回。Python的A/B各经`search_reassignment`和分阶段`search_*`提交候选，单候选策略同样适用。Java另有单候选默认入口。

B/C共用程序指定阶段的只读`context`和截止时间。局部编辑提供转入、转出任务和待修复相邻边。`LocalEvaluator.rebuild`授权重建整星，初始化调用`C.build`，重分配调用`C.rebuild`。从空轴重建时传入空时间轴、完整候选顺序及空的转入和转出集合。重分配可传入窗口偏好任务，由C决定用法，来源GREEDY据此排序窗口。

`LocalResult`返回`APPLIED`及完整本星时间轴，或正常返回`NO_FEASIBLE_CHANGE`，后者的`LocalTrial.total_profit`为空。非法输出（包括声称成功却越权或不可行的输出）使组合失败，策略捕获后仍按失败处理。A返回`None`表示当前规则无后续移动，B返回`None`表示本次单星改进结束。一次移动未改善时，仍按搜索规则判断是否继续。

并发试评由运行时串行处理。B并发提交且C使用随机性时，抵达顺序可能改变随机流。同一种子和相同试评顺序可复现。

### 1.2 固定运行合同

- 单实例使用1核、2 GiB内存和5秒硬上限。计时包含A初始分配、候选预处理、搜索、输出和独立终验，公共数据读取另计。暂定4.5秒搜索，预留0.5秒收尾。
- 手工B暂用可搜索时间的40%（1.8秒）做初始局部优化，由各星均分。每次移动中，每颗受影响星暂用20毫秒。P3设计数据验收后校准这两项及收尾预留。RKHMA原生B按来源种群和局部搜索规则使用全实例截止时间。
- 默认仅接受总收益严格提高的完整移动。手工路径在受影响星的副本上试改，移除转出任务后检查新相邻转换边。各受影响星均可行且满足接受条件时整体提交，否则撤销。未受影响的时间轴与未授权观测保持原样。
- RKHMA重分配保留迁移、替换、交换、任务束和后续校准，接受迁移后可重算全星时间轴。A3完成内部重分配与校准后，可返回收益未严格提高的方案。搜索截止时返回已保存的较高收益可行检查点。组合输出须经完整问题验证。
- 纯手工路径的重分配轮数不限。RKHMA默认最多25轮，沿用来源停滞条件。搜索到期返回此前可行调度，硬超时记失败。
- 手工随机流按实例、求解种子、阶段、模块、移动及卫星分流。RKHMA原生模块沿用来源随机键和逐星种子，所有随机流均排除候选代码哈希。冻结代码求解实例时不调用LLM。

`A3B3C3`固定配置为`410000`。所有规模沿用来源不超过500任务时的策略。A3使用复合初始分配策略7，停用初始跨星修补。B3先经C构建并验证各星基准调度，再做完整搜索，默认对有任务且无继承状态的卫星执行两次种群搜索。来源用于4000及以上任务的搜索缩减和延迟校准分支停用。优化器用微小的转换余量奖励区分同收益候选，最终评价只计合法观测的原始收益。来源入口和重组运行时默认按确定性顺序提交逐星结果，调用方可显式关闭。

项目以Python为目标语言。`satellite_scheduler.runtime.contracts`定义两阶段消息和预算，`satellite_scheduler.runtime.solver`支持手工模块与RKHMA A3/B3/C3组合。P1保留的Java对照采用`method.runtime.SolverContracts`驼峰接口，由`TwoStageSolver`组织初始化、副本编辑、权限检查和整体接受。`RkhmaAllocation`、`RkhmaHybridSearch`与`RkhmaGreedyDecoder`直接实现统一A/B/C接口。`RkhmaRuntime.Components`接收同一组接口，为来源模块启用快速内核，自定义模块经受控试评接入。

Java的250任务、1秒内部记录重分配对照中，通用组装、来源快速路径和原版的收益、归属及观测一致。300任务对照中，通用路径在4.5秒返回已验证检查点，快速路径完整结束。来源对照结论限对应夹具和运行条件。非1秒内部间隔按本项目合法候选适配，逐步等同性未获证实。[统一报告](../Results/Reports/p1-rkhma-unified.md) · [迁移证据](../Results/Evidence/python-migration/evidence.md)

Windows的`scripts/run-manual.ps1`及`scripts/run-python-manual.ps1`对进程组执行单核、2 GiB Job总提交内存及公共数据读完后5秒硬截止。Python的求解和独立验证进程在计时前分别读场景，验证进程在硬截止前用自己的场景重建输出并核对可行性与收益。脚本核查两进程的Job、单核亲和性及Normal优先级。直接调用同进程`TwoStageSolver`仅提供协作式截止检查，`ForkedSolver`仅强制时间截止。操作系统级CPU和内存上限由启动方设置。P2任务4负责实现并验收生成代码的隔离执行与独立终验。[验收报告](../Results/Reports/p1-two-stage-runtime.md)

### 1.3 案例与生成协议

A/B/C分别维护可扩充案例库，规模参考百条级，无统一上限。先导前冻结实际条数。决策逻辑相同的改名或调参版本合并并保留来源。不同逻辑的完整实现可分别收录，入库无需主观价值评判或预先证明收益更高。案例可取自现有实现或项目自主设计，论文和作者源码均非必需。

每条必填`case_id`、`category`、`description`、`code`。A/C的`code`包含完整角色实现，B的每条案例包含所属阶段的完整实现及必要依赖。片段和缺少关键逻辑的包装只作线索。入库允许尚未适配两阶段接口。按迁移需要分别说明时间表示和可作的决策，并补充接口差异、依赖、局限。来源案例可按核心思想适配，描述须符合实际代码和运行合同。原样保存、精确复现及来源版本按各自要求核验。

JSON元数据与源码在案例目录中分开保存，检索或冻结前校验源码并还原为完整字符串。`description`按实际阶段和算子说明决策与门禁。[保存规则](案例入库与接口适配.md#实际保存位置) · [描述标准](案例入库与接口适配.md#案例描述标准)

用户于2026-11-14确认现有入库案例可用于本项目外部模型检索和代码生成。按`case_id`和当前`case_sha256`关联后台来源及既有审核记录。已确认的案例无需另交许可证文件，也不因缺历史审核字段新增检索门槛。后台`source`和许可信息留在后台，Retriever提示和固定案例包的提示内容均不携带。

每次独立演化仅在初始化调用一次Retriever。请求覆盖A/B/C，提供当前问题、接口及按模块和B子库组织的`case_id`、`category`、`description`。默认用描述展示候选，按需附接口或代码摘录，本地读取完整源码用于版本校验。可提供全部去重合格候选。容量不足时，调用前确定并记录预筛规则，按实际提供的候选计算配额，禁止静默截断。

Retriever返回选中案例ID和针对当前问题生成的适配说明。A、C按实际提供的去重合格候选数 $M_m$ 计算返回数量。

$$
k_m=\lceil0.05M_m\rceil,\qquad M_m\ge1,\quad m\in\{A,C\}.
$$

B的两个子库分别覆盖初始单星优化和重分配后单星局部调整。每个案例ID只归属一个子库。实际提供的去重合格候选数分别为 $M_{B,\mathrm{init}}$ 和 $M_{B,\mathrm{post}}$，两库均须非空。总数 $M_B=M_{B,\mathrm{init}}+M_{B,\mathrm{post}}$ 用于计算B的配额。

$$
k_B=\max\left(2,\left\lceil0.05M_B\right\rceil\right).
$$

B每个子库至少选1条，其余名额从本次B候选中选。两个阶段各按适用性选择，无需同源或预先配对。A、C或任一B子库缺少合格候选时，调用前报告具体缺项并停止初始化。程序核对数量、ID、模块、B子库覆盖和去重，记录库总量、各子库实际候选数、配额和返回清单。

5%参考PaperBanana方法图中的10/200，原实现使用固定Top 10。B两个子库各至少1条是本项目的覆盖要求。[方法参照](../Knowledge/算法设计方法参照.md)

校验通过后，程序从本次固定候选中取出选中案例的完整`code`，与适配说明一并冻结，供同一次独立演化的全部链和轮次复用。生成时各角色用本模块选中案例的源码和适配说明作参考。B可按阶段借鉴、适配或另行设计，完整B模块仍须支持两个阶段。

生成结果只含分阶段的`description`和本模块完整`code`。Python代码提供无参`Strategy`类，直接实现本模块的两阶段接口。程序保存实际提示，并绑定本轮共同`base_algorithm_hash`和`target_module`。[描述标准](案例入库与接口适配.md#案例描述标准)

### 1.4 演化与Critic

1. 个体由完整A/B/C组合及固定运行配置组成。初始化从合格已有方法抽样或用LLM生成，经验证、评价和去重后补足N个。额外初始化开销另记。
2. 每代仅为代初N个个体各启动一条改进链。链间可并行，链内按轮次顺序执行。
3. 同链同轮冻结一个只读完整父版本。A/B/C共读该版本及各自对应的案例、反馈和记忆，只修改本模块。代码解析、签名或权限检查失败时，责任模块最多修复1次，再冻结本轮新版本。
4. 程序处理全部8种搭配，含原父版本、3个单改、3个双改和1个三改。通过门禁的搭配逐实例复用完整匹配的评价，未命中则求解。含未通过静态门禁改动的搭配逐项记失败。单改下降或失败时，其余搭配照常处理，以保留配对和交互对照。[评价复用规则](#16-三类记录与评价复用)
5. 每轮评价后调用Critic一次，读取全部8项的描述、代码、逐实例结果、失败与有效交互统计，输出A/B/C建议、短期反思和共享交互反馈。每代结束总结一次全部链的长期经验。
6. 程序在各链本轮的全部有效搭配中独立选下一轮父版本。新候选均下降或失败时保留原版。首轮使用固定案例和已有长期记忆，首轮Critic在评价后生成本链反馈。
7. 代末程序将旧种群与各链各轮的全部有效候选合并去重，取前N个。旧版、早轮候选及双改和三改按同一规则竞争。
8. 轮间和代末依次按整体J降序、规定运行的平均耗时升序、代码哈希字典序升序排名，仅纳入已完成的有效记录。外部中断恢复后补齐本轮。调用、token或候选总量上限不得截断八项。

### 1.5 分模块记忆与交互

A/B/C分存各自的短期反思和长期记忆，协同和冲突记入共享交互经验。新链清空短期缓冲，同代共用长期快照，代末统一更新供下一代使用。

启动时每模块及共享区默认各留6条长期经验。生成提示各取本模块和相关共享经验最多2条。短期各留最近2轮，本模块与相关短期交互合计约1000 tokens。

经验只存建议、适用条件与评价事件引用。成绩、失败和目标变化从评价记录读取。经验用于指导搜索，无需逐条复验或满足入库次数。程序仅核对引用、版本和数值。Critic解释结果，成因推断标为待验证假设。

Critic固定其他搭档比较模块改动，例如在4种相同B/C背景下配对比较A0/A1。成绩属于完整组合。程序用同条件下的有效组合计算交互。记 $J_{ijk}=J(A_i,B_j,C_k)$。

$$
I_{AB}=J_{110}-J_{100}-J_{010}+J_{000},
$$

$$
I_{ABC}=J_{111}-J_{110}-J_{101}-J_{011}
+J_{100}+J_{010}+J_{001}-J_{000}.
$$

AC、BC及另一搭档背景同理。所需对照均有效且已完成时才计算，禁止用0分填补。单改、双改和三改的实际记录均可用于轮内反馈和代末总结。

### 1.6 三类记录与评价复用

- **候选记录**包括版本标识（复用代码哈希）、描述与代码、父版本、修改模块和`run_id`，关联生成调用及评价记录。
- **评价记录**包括候选、阶段、实例、求解种子、调度、收益、耗时和状态，失败附原因。整体J由规定评价汇总。
- **运行级公共信息**包括问题与接口合同、数据及程序版本、环境、预算、模型参数、实例与种子清单、固定案例包及后台来源引用。每次运行保存一份，以`run_id`关联。公共条件变化时另建记录。

提示、回复、用量、反思、轮间继承与筛选按事件存一次。保存完整提示后，候选记录可省略重复的案例和记忆ID。

缓存要求代码、配置、评价阶段、实例、求解种子、内核、运行时、接口、验证器与环境全部匹配，公共项从运行记录读取。命中沿用原评价事件ID及来源运行，禁止复制结果或记为新执行。

生成代码运行环境禁止联网和访问验证、测试集。内核只读，终验在生成代码进程之外独立执行。

- 两条件共用实例、内核、求解种子、运行环境和第1.2节的计时及接受规则，执行顺序交错。

## 二、数据、评价与正式比较合同

### 2.1 数据生成与划分

- 设计、验证、同分布测试、分布外测试各6例。每分区按“任务数/卫星数”50/2、100/2、200/4、300/4、400/6、500/6各取1个独立实例。
- 设计每例1个求解种子，验证与测试每例2个。演化后按设计成绩冻结去重后的前2个完整算法参加验证。
- 四分区按共同母场景分组且互斥。前三分区采用区域模式，分布外测试采用全球模式。分布外仅改变目标空间分布，其余生成与物理条件一致。仅更换种子仍属同分布。
- 冻结实际路径、源文件与生成器版本、实例生成种子和构造参数。生成种子与求解种子分别记录。只有设计分区的结果进入提示和记忆。

生成器来源已确认。P3在本项目的隔离副本中适配显式生成种子并生成数据，再做加载验收。原程序和共享Scene只读。[指定生成器](../Knowledge/Source-Provenance.md#本轮实验数据的指定生成器) · [P3阶段计划](../Plan/mechanisms/P3-小预算先导与冻结选型.md)

### 2.2 评价与失败合同

P2控制程序与P3先导共用下列评价规则。问题目标为实际完成任务的原始收益。

$$
R(H,x)=\sum_{i\in\text{实际完成任务}}p_i,\qquad
U_x=\sum_{i:\,\text{存在合法观测候选}}p_i,\qquad
q(H,x)=R(H,x)/U_x.
$$

`score`为整体J。归一化收益先在各实例内按求解种子平均，再在各规模内按实例平均，最后对六种规模等权平均。$U_x$只作归一化分母，$U_x=0$的实例只作正确性诊断。按固定顺序用未舍入值聚合，耗时只用于收益同分时的排序。[排序规则](#14-演化与critic)

- 可行调度记成功，`raw_profit`与`evaluation_profit`均填实际收益。合法空调度收益为0。
- 非法输出、接口错误、异常或硬超时记失败，`raw_profit=null`、`evaluation_profit=0`。失败的0分仅用于实验汇总，设计入选、验证排名和交互归因均排除失败项。
- 外部中断记未完成且不计分，按原条件补齐。算法自身的失败保留失败身份。
- 设计阶段仅允许所有规定运行均成功的完整候选进入种群。验证任一次失败即取消资格，保留其余规定记录并继续处理其他候选。只有完成全部验证且零失败的候选有资格成为胜者。
- 验证均失败时记录选型失败，停止该条件的测试。候选名额和资格门槛固定，第三名及以后不补位。手工基线独立遵守同一资格规则。
- 冻结唯一验证胜者、配置与种子后再测试。失败记录保留，按0分计入全部规定运行的主均值。禁止重跑覆盖失败或按测试结果重选。两类测试分别报告，逐实例种子均值相等记平局。
- 报告原始及归一化收益、逐规模结果、胜平负、低分位、耗时P50/P95、失败率和实际用量。失败耗时计入汇总，主成绩包含失败。
- 保留选型失败的独立演化重复。独立盲测使用此前未查看的数据。1次独立演化只支持流程和初步结果，显著性或稳定泛化需另有证据。

### 2.3 先导用量与证据记录

按第1.7节估算。若32轮父版本均完整命中缓存，其余候选无重复和失败，每轮新增7个完整组合、42次实例求解（每个组合6个设计实例）。计入初始种群后，设计阶段共232个完整算法评价需求、1392次实例求解。

- 主方案加验证24次、测试24次，共1440次实例求解。最佳手工种子新增36次，合计1476次，按每次5秒约2.05核小时。实际执行量随缓存、重复及失败变化，这些数值仅用于估算。

分别记录搭配数、实例评价缓存命中数、实际求解次数及耗时、各角色调用次数及耗时、实际输入及输出token。复用只记命中，数据生成与校准成本另计。

原始现场存于`outputs/<run-id>/`，验收和实验结果沿用`vault/Results/Evidence/<id>/`及`vault/Results/Reports/<id>.md`。记录实际命令、cwd、数据来源、合同版本、实际Python或Java环境与Normal优先级。评价事件和版本按第1.6节关联。既有证据完整且身份与条件匹配时可复用，结论限原范围，执行量只计一次。

### 2.4 正式比较与结论强度

P4按待支持的主张安排对照，P1—P3沿用各自验收条件。

- 声明性能优势时，使用同问题、同实例求解合同的强传统或自动设计基线，如实比较设计成本。
- 归因全组合、记忆、检索或解码贡献时，选择相应消融。模块冻结、B输入扰动和记忆消融按主张选用。
- 报告最优差距时再定精确模型、求解工具、规模及超时报告。CP-SAT及候选节点上限当前未定。
- 正式实验使用新的独立测试证据。同预算优势需有匹配的设计成本。独立演化重复由独立运行获得，同实例的求解种子用于实例内重复。
