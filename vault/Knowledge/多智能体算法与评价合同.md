## 一、共享方法合同

### 1.1 两阶段接口与职责

这里的初始化指单个实例的初始调度。程序用独立函数`initialize_schedule`组织初始化；初始化策略仍属于A/B/C，随各自模块一起演化。
每个模块版本完整支持初始化与重分配两个阶段，不增加初始化智能体。

```text
A.initial_assign(problem, api, budget, rng) -> Assignment
A.propose_move(problem, api, state, feedback, budget, rng) -> Move | None
A.search_reassignment(problem, api, state, feedback, evaluator, budget, rng) -> MoveTrial | None

B.search_initial(problem, api, view, evaluator, budget, rng) -> InitialTrial
B.search_initial_local(problem, api, view, context, feedback, evaluator, budget, rng) -> LocalTrial | None
B.search_reassignment(problem, api, view, context, feedback, evaluator, budget, rng) -> LocalTrial | None
B.search_calibration(problem, api, view, context, feedback, evaluator, budget, rng) -> LocalTrial | None

MoveEvaluator.evaluate(base, move) -> MoveTrial
MoveEvaluator.calibrate(base) -> MoveTrial
MoveEvaluator.checkpoint(trial)
InitialEvaluator.evaluate(priorities) -> InitialTrial
LocalEvaluator.evaluate(plan) -> LocalTrial
LocalEvaluator.rebuild(priorities, preferred_window_tasks) -> LocalTrial

C.build(problem, api, view, priorities, budget, rng) -> SatSchedule
C.apply_local(problem, api, view, context, plan, budget, rng) -> LocalResult
C.rebuild(problem, api, view, context, priorities, budget, rng) -> SatSchedule
```

- **A**：初始化依据问题数据返回全部任务的初始归属，允许`None`；不在初始化中根据C的解码结果试探跨星迁移。重分配读取当前完整调度，提出转移、交换、放弃或分配无归属任务的差分。A不能改写窗口、时刻或时间轴。
- **B**：负责本星任务顺序与搜索，可以反复调用C评估候选；重分配选择本星的任务、取舍与处理顺序，也可以选择全部本星归属任务。B不能改变任务归属。
- **C**：初始化按B的列表构造调度；局部编辑只修改B授权任务。B需要从空时间轴重建完整本星候选时，重分配阶段调用`rebuild`，而不调用初始化的`build`。

A的初始分配与重分配分别实现。B的初始单星搜索与重分配局部调整分别实现；初始化内部可以另做局部改进，但不能调用重分配策略。A1/A2的重分配策略和B1/B2的局部策略也分别实现。候选访问、试评门禁和问题验证仍是公共基础能力，不属于策略复用。
手工B保留独立的初始化局部改进入口。B3的来源初始化执行单星混合搜索，不额外追加独立的初始化局部步骤；其重分配局部修补和全星校准分别实现。

`state`和本星`view`均为只读快照。`Assignment`保存每任务至多一个owner，非空owner须有合法观测候选。
`Move`保存`base_state_hash`、归属差分`edits`、额外修复卫星和全星校准标记，当前不限制单次归属变更涉及的任务数量。只重排卫星而不修改归属时，可指定修复卫星；全星校准必须覆盖所有卫星且不更改归属。
`LocalPlan`保存`base_view_hash`、允许移除或改时刻的`release`集合，以及有序的`reconsider`列表。已调度任务重插时须同时属于两者。
C不得扩大这些集合；暂不执行任务不等于取消其owner。`LocalResult`正常返回`APPLIED`及完整本星时间轴，或`NO_FEASIBLE_CHANGE`；声称成功却越权或不可行属于运行失败。

两阶段的调用顺序为：

```text
initialize_schedule:
  A.initial_assign
  各星 B.search_initial -> 反复试评 C.build -> 选择一个候选
  各星 B.search_initial_local -> 试评 C.apply_local 或 C.build，context.phase = "INIT"

重分配循环:
  A.search_reassignment -> 可反复试评完整移动及其后续候选
  受影响星 B.search_reassignment -> 试评 C.apply_local 或 C.rebuild，context.phase = "REASSIGN"
  来源策略需要时：全星 B.search_calibration -> 试评 C.rebuild
```

上述顺序适用于所有任务规模。B在初始化中可以反复请求C试评单星候选，再进入A的重分配；暂不为复现来源算法增加初始跨星调整的兼容路径。该决定不排除A依据窗口和负载等问题数据选择初始归属。

试评由运行时调用C并检查候选任务、卫星、编辑权限、可行性和截止时间；试评本身不提交时间轴。A和B只能返回或保存本次调用实际试评得到的候选；返回后试评入口失效。A可以用`MoveEvaluator.checkpoint`保存已经选择的可行候选，以便搜索截止时返回。无可行编辑正常返回`NO_FEASIBLE_CHANGE`，其`LocalTrial.totalProfit`为空；非法输出即使被策略捕获也使组合失败。
`LocalEvaluator.rebuild`授权重建当前整星：初始化调用`C.build`，重分配调用`C.rebuild`。简单策略可分别实现`B.initialPriority`、`B.proposeInitialLocal`和`B.proposeReassignmentLocal`；对应默认搜索入口各试评其返回的一个候选。更复杂的B可以分别覆写三个搜索入口并反复试评。
重分配重建可携带窗口偏好任务集合，C决定如何使用该偏好；来源GREEDY实现其窗口排序。简单A可实现`proposeMove`，复杂A可实现`searchReassignment`并比较或链式试评。`searchCalibration`是重分配阶段的全星重算入口；B3在此单独运行来源种群搜索，而常规局部调整使用来源增量修补或回退搜索。
并发试评请求由运行时串行处理；若B并发提交且C使用随机性，请求抵达顺序可能影响随机流。同一种子和相同试评顺序可复现。

B/C接收同一阶段的只读`context`与截止时间。局部编辑的上下文提供转入、转出任务及待修复相邻边；阶段由程序指定。
整星候选从空时间轴构建时，`rebuild`收到空的本星时间轴与完整候选顺序，转入和转出集合为空。
重分配不回调初始化接口。A返回`None`表示当前规则已无后续移动；B返回`None`表示本次单星改进结束，一次移动没有改善不终止整个求解。

### 1.2 固定运行合同

- 纯手工运行时在受影响卫星的副本上试改。移除转出任务后，检查新形成的相邻转换边；所有受影响星可行且总收益严格提高时整体接受，否则整体撤销。未受影响时间轴及未授权观测保持原样。
- RKHMA来源重分配保留迁移、替换、交换、任务束及后续校准逻辑。来源在接受迁移后可能重新校准全部卫星，因此该路径不保证未受影响星的时间轴保持不变。组合输出须通过完整问题验证。
- 默认只接受收益严格增长的完整移动。来源A3可在完成其内部重分配与校准后返回收益未严格增长的最终方案，以保留来源控制逻辑；搜索截止时返回已保存的较高收益可行检查点。
- 全实例使用1核、2GB内存、5秒硬上限，包含A初始分配、候选自己的预处理、搜索、输出与独立终验；公共数据读取另计。搜索截止暂设4.5秒，预留0.5秒收尾。
- 手工B的初始局部优化暂占可搜索时间的40%（1.8秒），按卫星数均分；每次移动、每颗受影响星暂用20毫秒。RKHMA原生B保留来源的种群和局部搜索，使用全实例截止时间。重分配不设额外任务数量上限。
- 40%、20毫秒及收尾预留是待校准的启动默认值，在P3设计数据验收后校准。纯手工运行时不设置重分配次数上限；RKHMA保留来源默认最多25轮及其停滞条件。到期返回此前可行调度，硬超时记为失败。
- 手工运行时按实例、求解种子、阶段、模块、移动及卫星分流。RKHMA原生模块保留来源的随机键及逐星种子规则；随机流均不使用候选代码哈希。冻结代码求解实例时不调用LLM。

2026-11-04根据用户要求取消原先暂定的4个额外任务上限。既有来源初始分配、种群搜索、重分配与解码对照仅支持对应夹具及运行条件；非1秒内部间隔使用本项目合法候选适配，不能声称逐步等同来源实现。

P1的Java接口位于 `method.runtime.SolverContracts`，方法采用Java驼峰命名；`TwoStageSolver`组织初始化、受影响星副本编辑、权限检查和整体接受。
`RkhmaAllocation`、`RkhmaHybridSearch`和`RkhmaGreedyDecoder`直接实现统一A/B/C接口。`RkhmaRuntime.Components`接收同一组接口，并在对应来源模块上启用来源协调器的快速内核；混搭的自定义模块通过受控试评接入。
`A3B3C3`按固定配置`410000`组装。所有规模沿用来源不超过500任务时的做法：A3使用复合初始分配策略7，不执行初始跨星修补；B3保留初始单星搜索，默认对有任务且无继承状态的卫星执行两次。来源针对4000及以上任务的搜索缩减与延迟校准分支不再启用。来源优化器内部使用微小的转换余量奖励区分同收益候选；最终评价仍只计算合法观测的原始收益。
250任务、1秒内部记录的实际重分配对照中，通用接口组装、来源快速路径与原版的收益、归属及观测一致。300任务对照中，通用路径在4.5秒搜索截止时返回已验证检查点；来源快速路径完整结束。具体条件和边界见[统一报告](../Results/Reports/p1-rkhma-unified.md)。
来源正式入口默认按确定性顺序提交逐星结果；重组运行时采用相同默认值，调用方仍可显式关闭。
Windows正式入口 `scripts/run-manual.ps1` 将运行进程组限制在单核和2 GiB Job总提交内存内，并在公共数据读取结束后执行5秒端到端硬截止。
直接调用同进程 `TwoStageSolver` 仅提供协作式截止检查；直接调用 `ForkedSolver` 只强制时间截止，操作系统级 CPU 和内存限制须由启动方提供。
P1手工策略及其来源见[验收报告](../Results/Reports/p1-two-stage-runtime.md)。生成代码的隔离仍属于P2。

### 1.3 案例与生成协议

A/B/C分别维护可扩充案例库，建设规模参考百条级候选池，按独立思路、来源和接口适用性建设；先导前冻结实际条数，不设统一固定上限。
每条核心内容只要求`case_id`、`category`、`description`、`code`。时间表示、接口差异和局限按实际迁移需要补充，不强制每条填写一整套元数据；时间表示与可选择哪些决策分别说明。
`source`及可核实的许可信息保留后台，按`case_id`追溯，不进入Retriever提示或固定案例包的提示内容。

Retriever每次独立演化仅在初始化时调用一次，依据问题与接口返回A/B/C案例ID和适配说明。适配说明针对当前问题生成，不要求在库中预填。
各模块按本次实际提供的去重合格候选数 $M_m$ 返回：

$$
k_m=\lceil0.05M_m\rceil,\qquad M_m\ge1.
$$

非空至少1条，空集报告缺失并阻止检索初始化。程序计算数量并核对ID、归属和去重，记录库总量、实际候选数、目标数和返回清单。
5%参考PaperBanana方法图设置的10/200，是本项目的比例规则；作者原实现使用固定Top 10，参见[方法参照](../Knowledge/算法设计方法参照.md)。
案例与适配说明在一次独立演化内冻结，供全部链和轮次复用。

A/B/C生成结果只含`description`与本模块完整`code`，两个阶段接口随模块一起返回。
程序绑定本轮共同`base_algorithm_hash`与`target_module`，保存实际提示，不要求模型回填版本、材料来源或成绩。

### 1.4 演化与Critic

1. 种群个体是完整A/B/C组合及固定运行配置。初始化可从合格已有方法抽样或由LLM生成，统一验证、评价、去重并补足N个；先导使用P1的8个手工组合，其他初始化开销另记。
2. 每代遍历代初全部N个个体，各自启动改进链。链间可并行，同链轮次顺序执行；本代候选不额外启动新链。
3. 每轮程序冻结一个只读完整共同父版本，A/B/C读取同一版本及对应案例、反馈和记忆，各自只修改本模块；代码解析、签名与修改权限门禁失败时，责任模块最多修复1次，再冻结本轮新版本。
4. 程序枚举原父版本、3个单改、3个双模块及1个三模块，共8种搭配，逐项门禁和完整评价。单改下降或运行失败不裁剪其他搭配；静态门禁失败的受影响组合逐项记失败，其余照常。
5. 每轮评价后调用Critic一次，统一读取全部8项的描述、代码、逐实例结果、失败与有效交互统计，输出A/B/C修改建议、短期反思及共享交互反馈。每代结束再总结一次全部链的长期经验。
6. 程序从全部有效组合中选下一轮共同父版本；所有新候选下降或失败时保留原版。不同链独立更新；首轮用固定案例与已有长期记忆，首轮评价后才产生本链反馈，不增加生成前Critic。
7. 代末将旧种群与本代各链各轮全部有效候选合并、去重，取前N个。旧版本、早轮候选及双/三模块重组统一竞争，不预留来源名额。
8. 轮间与代末均按整体J降序、规定运行的平均耗时升序、代码哈希字典序升序选择。失败或未完成记录不参与排名；外部中断恢复后补齐本轮，不以调用、token或候选总量上限截断8种搭配。

### 1.5 分模块记忆与交互

A/B/C各存自己的短期反思与长期记忆，协同和冲突单存共享交互经验。新链清空短期缓冲，同代读取同一长期快照，代末统一更新，下一代使用。
启动默认值为各模块及共享区长期各6条；生成提示取本模块最多2条及相关共享最多2条。短期各保留最近2轮，本模块与相关短期交互合计约1000 tokens。

每条经验只保存建议、适用条件与评价事件引用；成绩、失败及目标变化从评价记录读取。经验是搜索建议，不逐条安排独立复验或设置入库次数门槛。
程序只核对引用、版本和数值；内容解释由Critic负责，成因推断标为待验证假设，不要求程序证明自然语言建议正确。

Critic分析模块时固定其他搭档做配对比较。例如A0/A1在4种相同B/C背景下比较，不把完整组合成绩拆成模块独立适应度。
程序按同条件有效组合计算交互。记 $J_{ijk}=J(A_i,B_j,C_k)$，例如：

$$
I_{AB}=J_{110}-J_{100}-J_{010}+J_{000},
$$

$$
I_{ABC}=J_{111}-J_{110}-J_{101}-J_{011}
+J_{100}+J_{010}+J_{001}-J_{000}.
$$

AC、BC及另一搭档背景同理。所需对照有失败或未完成时不计算，不能用0分替代；单改、双/三模块重组的实际记录均可进入轮内反馈和代末总结。

### 1.6 三类记录与评价复用

- **候选记录**：版本标识（复用代码哈希）、描述与代码、父版本、修改模块及`run_id`，关联生成调用与评价记录。
- **评价记录**：候选、阶段、实例、求解种子、调度、收益、耗时与状态，失败附原因；整体J由规定评价汇总。
- **运行级公共信息**：问题与接口合同、数据及程序版本、环境、预算、模型参数、实例与种子清单、固定案例包及后台来源引用。每次运行只保存一份，通过`run_id`关联；公共条件变化另建记录，不覆盖旧条件。

提示、回复、用量、反思、轮间继承与筛选过程按事件留存一次。完整提示已保存时，不再强制候选单列重复的案例和记忆ID。
缓存匹配覆盖代码、配置、评价阶段、实例、求解种子、内核、运行时、接口、验证器与环境；公共项由运行级信息读取。命中沿用原评价事件ID及来源运行，不复制结果或记为新执行。
生成代码的运行环境禁止联网、访问验证/测试集，内核只读，独立终验在生成代码进程之外执行。

## 二、数据、评价与正式比较合同

### 2.1 数据生成与划分

本节合同归属P3，生成与验收见[P3阶段计划](../Plan/mechanisms/P3-小预算先导与冻结选型.md)。

- 设计、验证、同分布测试、分布外测试各6例。每分区按“任务数/卫星数”50/2、100/2、200/4、300/4、400/6、500/6各取1个独立实例。
- 设计每例1个求解种子，验证与测试每例2个；演化后按设计成绩冻结前2个去重完整算法参加验证，不从第3名补位。

数据由[已指定生成器](../Knowledge/Source-Provenance.md#本轮实验数据的指定生成器)在本项目隔离副本中准备，原程序与共享Scene只读。来源已确认，显式生成种子适配、实际生成及加载验收尚未完成。
前三分区使用区域模式，分布外测试使用全球模式；只改变目标空间分布，其余生成与物理条件一致，不能把仅更换种子称为分布外。
按共同母场景分组，四分区互斥；冻结实际路径、源文件及生成器版本、实例生成种子与构造参数，生成种子与求解种子分开。只有设计结果进入提示和记忆，验证/测试不反馈。

### 2.2 评价与失败合同

本节为P2控制程序与P3先导共用的已确认评价合同；P1工程验收见[P1阶段计划](../Plan/mechanisms/P1-可运行求解器起点.md)。

问题目标仍是实际完成任务的原始收益。为使不同规模等权，评价使用：

$$
R(H,x)=\sum_{i\in\text{实际完成任务}}p_i,\qquad
U_x=\sum_{i:\,\text{存在合法观测候选}}p_i,\qquad
q(H,x)=R(H,x)/U_x.
$$

`score`沿用整体J：先平均同实例求解种子，再平均同规模实例，最后六种规模等权。$U_x=0$的实例只作正确性诊断，不进入收益均值；$U_x$不是最优值，也不改变问题收益。
运行时间不与收益任意加权，同分时才按平均耗时、代码哈希排序，使用固定聚合顺序与未舍入数值。

- 成功且可行时，`raw_profit`与`evaluation_profit`均为实际收益；合法空调度是成功且收益为0。
- 非法输出、接口错误、异常或硬超时记失败，`raw_profit=null`、`evaluation_profit=0`。失败的0分只用于实验汇总，不用于设计种群、验证排名或交互归因。
- 外部中断记未完成，在原条件下补齐，不能冒充算法失败或已执行0分；算法自身失败不能改标为外部中断。
- 任一规定设计运行失败，该完整候选不进入种群。验证任一次失败即取消候选资格，其余规定记录继续保留且其他候选继续；只在完成全部验证且零失败的候选中选胜者。
- 验证均失败时记录选型失败，不测试、不补候选、不降低门槛。手工基线单独遵守同一资格规则。
- 验证通过后冻结唯一胜者、配置与种子再测试；测试失败保留并按0分计入全部规定运行的主均值，不删失败、不重跑覆盖、不因测试结果重选。两类测试分别报告，逐实例种子均值相等记平局。
- 报告原始与归一化收益、逐规模结果、胜平负、低分位、耗时P50/P95、失败率及实际用量。失败耗时计入汇总，成功结果的条件均值不能替代含失败的主成绩。
- 选型失败的独立演化重复保留；已查看的先导测试不能继续充当后续独立盲测。1次独立演化只支持流程与初步结果报告，不声称显著性或稳定泛化。

### 2.4 正式比较与结论强度

以下要求归属P4，按待支持主张决定具体对照，不增加P1—P3前置门槛。

- 要声明性能优势，再选择同问题、同实例求解合同的强传统或自动设计基线，并如实比较设计成本。
- 要归因全组合、记忆、检索或解码贡献，再选择相应消融；模块冻结、B输入扰动、记忆消融等在此决定，不列为第一版工程门槛。
- 要报告最优差距，再决定精确模型、求解工具、规模与超时报告方式；当前不预设CP-SAT或候选节点上限。
- 正式实验使用新的独立测试证据。不同设计成本的最终成绩不表述为同预算优势，增加同实例求解种子不能替代独立演化重复。
